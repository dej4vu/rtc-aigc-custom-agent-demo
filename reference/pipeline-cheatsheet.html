全流程速查表

按一次真实通话的记忆顺序整理：先定位层，再看事件，最后看数据格式。

七层链路

  1. Browser：进房、采集麦克风、发布上行、订阅并播放下行。
  2. RTC：传输实时音频与二进制消息，屏蔽端侧网络细节。
  3. MMPG Gateway：接入自有 Agent，转发音频/事件，也承载 ASR 编排。
  4. ASR：把用户音频流识别成 started / delta / done 文本事件。
  5. Node Agent：接收 done 文本，维护轮次、上下文、取消和 Trace。
  6. LLM：Ark Chat Completions 流式产出文本 delta。
  7. TTS：按句合成 PCM，再经 Gateway 变成 assistant.audio.delta。

关键事件

方向事件 / 接口用途
Agent → MMPGsession.create创建会话并声明 ASR、音频格式。
MMPG → Agentuser.audio.transcription.done触发一次新回复。
Agent → LLMArk chat.completions流式生成文本。
Agent → TTSSeedTTS JSONL streaming按句合成 Base64 PCM。
Agent → MMPGassistant.audio.delta回传音频块；最后一块 done=true。
Agent → MMPGassistant.audio.cancel打断后取消旧音频。
Agent → Browserassistant.messageTrace 和自定义字幕。

本项目硬约定

  • TTS 输出是 24 kHz PCM，对应 MMPG pcm24。
  • 每句可独立合成，降低首包延迟；多句共用同一 TTS turn 上下文。
  • 用户再次说话时取消旧 LLM/TTS，清空队列，递增 resp_id。
  • 情感标签送给 TTS；字幕和历史消息先清洗标签。
  • 密钥只在服务端；浏览器只拿一次性 RTC Token。

排障顺序

  1. 服务健康：GET /health。
  2. 凭证与 Bot：yarn preflight。
  3. MMPG 参数：yarn probe。
  4. 浏览器麦克风与 RTC 发布。
  5. 按 Trace 检查 client.ready → ASR → LLM → TTS → playback。
