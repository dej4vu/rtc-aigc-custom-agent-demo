Lesson 003

ASR done 之后，谁拥有这次回复？

第 2 课解决了“会话启动”。这一课回答实时 Agent 最难的问题：LLM 和 TTS 都在流式运行时，如何表示一次回复，又如何安全放弃它。

你将获得的小胜利

你能用三个所有权模型解释打断：resp_id 决定哪路音频还能被网关接受，AbortController 决定哪些网络请求停止，ttsQueue 决定哪些待合成文本丢弃。

一次回复的生命周期

  1. ASR done：最终文本非空。控制器把用户文本压入历史，修剪上下文，创建新 turn。
  2. 创建 turn：respId += 1；生成 AbortController；状态进入 THINKING。
  3. LLM delta：累积全文，推送未定字幕；文本同时进入 SentenceSegmenter。
  4. 句子成熟：硬断句或超过 80 字触发切分；可读文本清洗 Markdown 后进入 TTS 队列。
  5. TTS chunk：第一个 Base64 PCM 解码成功后进入 SPEAKING，并通过 assistant.audio.delta 携带当前 resp_id 下行。
  6. 最后一包：只有当 LLM 已完成且 TTS 队列为空，才发送空 payload、done=true。
  7. 播放完成：网关回 assistant.audio.done 且 resp_id 匹配，turn 进入 FINISHED。

源码：server/lib/turn-controller.js:331 到 server/lib/turn-controller.js:601。

为什么必须串行 drain TTS？

drainTtsQueue() 用一个 ttsDraining 标志保证同一时刻只有一个 speakJob() 在消费队列。这不是为了性能保守，而是为了保序：

  • 句子 1 的 PCM 必须先于句子 2 到达网关。
  • 只有所有旧句发送完、LLM 完成、队列为空，才能判定下一包是 done=true。
  • 打断时清空队列即可让旧回复停止；正在进行的 fetch 由 AbortController 取消。

打断的原子边界

用户再次说话时，user.audio.transcription.started 不是简单改状态。它触发五件事：

turn.cancelled = true;
turn.abort.abort();
ttsQueue.length = 0;
respId = oldRespId + 1;
await sendMmpgEvent("assistant.audio.cancel");

源码：server/lib/turn-controller.js:603。这里没有数据库事务，但五个动作共同形成逻辑原子性：迟到的 LLM 回调用 cancelled 丢弃，网络请求用 signal 停止，旧音频用递增 resp_id 失效，网关播放用 cancel 命令停止。

开发方式迁移：修改这类系统前先问三个问题：谁拥有这次回复？谁负责取消？哪个事件代表真正完成？不要把取消逻辑分散到 LLM、TTS 和 UI 中；它们都应服从 TurnController 的 turn 所有权。
