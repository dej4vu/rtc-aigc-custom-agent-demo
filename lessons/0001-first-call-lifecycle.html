Lesson 001

一次通话从哪里开始，到哪里结束？

先不要陷入代码细节。你只需要把「发起、进房、听、想、说、打断、退出」七个动作装进同一张地图。

你将获得的一个小胜利

读完本课，你应该能不看代码说出：用户说一句话后，系统为什么知道要调用 LLM，LLM 的文本为什么能变成 RTC 下行音频，以及打断时旧答案去哪了。

全链路地图

发起浏览器请求业务服务端，拿到 RTC Token。
进房RtcClient joinRoom，采集并发布麦克风。
建会话Node 服务签名连 MMPG，发 session.create。
听MMPG ASR 产 started / delta / done 事件。
想done 文本触发 Ark LLM 流式回复。
说分句调 SeedTTS，PCM 回传 RTC 播放。
打断/退出取消旧任务、递增 resp_id，或关闭会话。

这张图中的「听、想、说」才是业务开发的核心边界：RTC 负责可靠实时传输，MMPG/ASR 负责语音入口，你的 Agent 负责编排，LLM/TTS 是可替换的能力服务。

一次用户提问的事件轨道

T+0user.audio.transcription.started用户开始说话；若有旧回复，先准备打断。
T+1user.audio.transcription.delta增量识别文本，可用来观察状态。
T+2user.audio.transcription.done最终文本确定；Agent 建一个新 turn。
T+3Ark chat.completions把文本送入上下文，流式接收回复。
T+4SeedTTS streaming按句合成 PCM，不等整段回复。
T+5assistant.audio.deltaBase64 PCM 回传；最后一包 done=true。
T+6assistant.message发送纯文本字幕与 Trace。

关键延迟优化不是「让 LLM 更快说完」，而是让第一句尽快可播：LLM 一出现可结束的句子就交给 TTS，TTS 一出音频块就回传 RTC。

为什么要用 Gateway，而不是浏览器直连模型？

  • 安全：AK/SK、ASR Key、Ark Key、TTS Key 都留在 Node 服务端。
  • 实时：麦克风音频经 RTC 上行，避免业务服务器自己接收高并发媒体流。
  • 可控：轮次、上下文、人设、取消和 Trace 都在你的自有 Agent。
  • 可替换：换 LLM 或 TTS 时，主要改 Agent 编排，不改浏览器通话壳。
