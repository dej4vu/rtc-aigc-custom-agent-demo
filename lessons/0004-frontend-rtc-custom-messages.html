Lesson 004

浏览器只做两件事：传音频，收发消息

服务端协议已经打通。这一课把前端收窄成两条通路：麦克风和 AI 音频走 RTC 发布订阅；client.ready、字幕、状态和 Trace 走 RTC 二进制自定义消息。

你将获得的小胜利

你能解释为什么 client.ready 必须等双 ready，能读出 cmsg TLV 的 8 字节结构，也能判断无字幕、无欢迎语该查前端还是查服务端。

点击通话后的真实顺序

  1. RTC 能力检查：VERTC.isSupported()。
  2. 启动云端会话：前端 POST /session/start；服务端确认 MMPG 后返回 callId、agentUserId、RTC 配置和 Token。
  3. 创建 engine：用 AppId 创建引擎，注册 AI 降噪扩展；失败时降级继续。
  4. 绑定事件：特别是远端加入、远端发布音频、二进制消息和自动播放失败。
  5. 进房：isAutoPublish:true、isAutoSubscribeAudio:true、chat 房间模式。
  6. 枚举设备并启动麦克风：完成后调用 markMicReady()；即使失败也会兜底置位，保证会话能继续。
  7. 等待 Agent ready：远端 Agent 加入或发布音频时调用 markAgentReady()。
  8. 发送一次 client.ready：双 ready 满足后发送；3 秒定时器是防卡死的强制兜底。

源码：web/src/lib/useCommon.ts:205、web/src/lib/RtcClient.ts:255、web/src/lib/listenerHooks.ts:61。

为什么 3 秒强制 ready 不是侥幸？

正常路径要求 Mic ready 和 Agent ready。但真实网络里，Agent 加入事件可能迟于麦克风准备完成，浏览器权限弹窗也可能阻塞用户操作。Demo 的选择是：正常事件优先，3 秒后允许 force ready。这样欢迎语最多晚一点，不会因为单个事件丢失而永久无声。

注意边界：force ready 只解决“事件迟到”，不解决“麦克风权限被永久拒绝”。后者要在设备权限和 RTC 错误日志里排障。

自定义消息不是普通 WebSocket

浏览器没有直连 MMPG。控制消息挂在 RTC 二进制消息通道上：

  • 出站：浏览器调用 sendUserBinaryMessage(agentUserId, bytes)。
  • 包装：encodeMmpgMessage() 使用 cmsg TLV 包装一层普通 JSON。
  • 入站：MMPG 的自定义消息经 assistant.message 进入 RTC，触发 onRoomBinaryMessageReceived。
  • 解析：parseMmpgMessage() 兼容 UTF-8 JSON、Base64 JSON、cmsg TLV 和旧版 subv / conv / tool / func / ctrl TLV。

TLV 结构只有 8 字节头：

0-3  magic：cmsg、subv、conv...
4-7  value 长度，big-endian uint32
8-N  UTF-8 JSON

关键陷阱：出站只包一层。测试 web/src/utils/mmpg.test.ts:96 明确要求 magic 是 cmsg、长度等于剩余字节、内层 JSON 没有二次字符串化。

入站消息如何变成 UI

类型作用前端处理
convLISTENING / THINKING / SPEAKING / INTERRUPTED / FINISHED更新 AI 状态；收到任何有效 Stage 也会标记 AI ready。
subv用户与 Agent 字幕按 userId、definite、paragraph 合并历史。
trace服务端链路事件进入 Trace 面板，显示延迟和 respId。
client.interrupt手动打断出站；服务端调用 cancelCurrent。

源码：web/src/utils/handler.ts:86、web/src/lib/listenerHooks.ts:275。

退出不是 leaveRoom 一行

正常挂断先停采集，再请求 /session/stop，最后 leaveRoom() 并销毁 engine。顺序很重要：先停采集可减少上行噪声；服务端 stop 会关 TurnController 和 MMPG；销毁 engine 是浏览器最后清理。页面卸载无法保证 fetch，所以用 navigator.sendBeacon() 兜底。

开发方式迁移：不要把业务状态散落在 RTC 回调里。RTC 回调只负责“收到原始消息/设备事件”，解析器负责归一化，Redux handler 负责状态更新，RtcClient 只负责发送和生命周期。
