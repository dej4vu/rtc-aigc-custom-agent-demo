Lesson 006

从“能跑”到“可交付”

前五课拆开了七层链路。这一课把它们重新压缩成一个开发循环：静态健康 → 外部凭证 → 网关参数 → 自动化行为 → 真实浏览器 → 清理。

你将获得的小胜利

你能在一次改动后按固定漏斗验收，并用 Trace 停住的位置判断故障属于哪一层，而不是凭感觉重启或乱改配置。

为什么顺序不能乱？

真实故障最容易被错误观察放大。如果服务都没健康就去浏览器试音，你会同时怀疑前端、RTC、MMPG、LLM 和 TTS。反过来，外部依赖全部确认后再进浏览器，任何失败就只剩你的改动和集成边界。所以先做便宜的确定性检查，再做贵的真实链路。

验收漏斗训练

按从左到右、可自动化的顺序点击。

当前仓库的真实基线

我在本课准备时重新运行了自动化测试：

yarn --cwd server test
# 37 passed, 0 failed
CI=true yarn --cwd web test --runInBand
# 4 suites passed, 16 tests passed

这个数字不是永远契约；它是今天的已知基线。你改代码后应比较差异：通过数量为什么变化？新增测试是否覆盖新行为？旧测试失败是否暴露真实回归？

六层验收命令

  1. curl -s http://127.0.0.1:3101/health：看 ok=true、issues=[]、activeCalls。
  2. yarn preflight：验证配置、AK/SK、Bot。加 -- --handshake 可只验签名握手。
  3. yarn probe：真实创建一次 MMPG session，确认 ASR 参数和 RTC 身份。
  4. yarn test：同时跑服务端和前端行为规格。
  5. yarn --cwd web build：确认生产构建；生产路径固定为 /rtc-demo/。
  6. yarn dev：浏览器验证欢迎语、至少两轮对话、打断和显式挂断。

用 Trace 定位，而不是猜

最后出现的 Trace下一步检查
无 mmpg.session.createdyarn probe；AK/SK、ASR、RTC 参数。
无 client.readyengine、agentUserId、Mic ready、Agent ready、cmsg TLV。
无 asr.done麦克风权限、isAutoPublish、ASR Key/Resource、上行音量。
无 llm.first_tokenArk Key、模型、网络、AbortController 是否误触发。
无 tts.first_chunkTTS Key、speaker 授权、JSONL error、pcm/24000。
无 playback.startedassistant.audio.delta、done 包、浏览器自动播放。
无 turn.finishedresp_id 匹配、done 事件、finish timer。
挂断后 activeCalls 不为 0/session/stop、gatewayClose、sendBeacon。

浏览器场景验收

一次合格验收至少包含四个场景：

  1. 欢迎语：进房后 client.ready 恰好 1 次；字幕无标签；有音频。
  2. 两轮对话：每轮都有 ASR done → LLM → TTS → playback → turn.finished。
  3. 打断：AI 播放中说话；出现 barge_in，旧 resp_id 作废，新回复更高。
  4. 清理：点挂断；MMPG 关闭；activeCalls=0。

仓库已经留下一次真实凭证回归：docs/verification.md:35。你不需要重复历史结论，但要用同样标准验收自己的改动。

检索练习

浏览器说“有 LLM 字幕但没有声音”，在 probe 已通过、Trace 已到 llm.done 的前提下，第一优先检查哪组？

微任务：给一个改动写验收单

假设需求是“把默认音色从撒娇学妹 3.0 换成另一个已授权音色”。请按六层漏斗写出：

  1. 必须修改的配置和可能需要改的测试断言。
  2. 必须跑的命令与每层通过标准。
  3. 浏览器最低场景集。
  4. 如果浏览器 403，你的第一处理动作。

同时运行完整基线：

yarn test

把验收单和结果发我。这是本课程的结业练习。

开发方式沉淀：你现在已经掌握的不是六个 API，而是一条实时 Agent 开发方法——先定义业务边界，再封装协议层，把流式文本与音频交给状态机，用测试锁住取消和完成语义，最后用固定漏斗交付。以后接入新模型、新 TTS 或新 RTC 平台时，沿用这个骨架。
